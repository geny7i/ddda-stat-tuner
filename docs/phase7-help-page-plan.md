# Phase 7 チャート廃止・使い方ページ追加計画

## 位置づけと実現可能性

`workspace/phase7.md` の要望を、現行実装を確認したうえで実装仕様・PR分割・受け入れ条件に整理する。Git管理外の `workspace` を参照しなくても実装とレビューができるよう、要望をこの文書に取り込む。

計画は実現可能。現在のチャートページは育成計画と同じ状態・ステータス計算・職業比較を利用しており、専用ページを削除しても育成計画内の成長値・スコア表示を維持できる。Markdown表示と目次生成は表示層に追加でき、成長表、探索アルゴリズム、共有コード形式の変更は必要ない。

ただし、次の2点は実装時に対応する。

- `HashRouter` の経路と通常の見出しリンクの `#` が衝突する。目次の移動には使い方経路内のクエリを利用する。
- `EditorHelp` のダイアログCSSを `CharacterTypeSelector` も使用している。ヘルプ削除と同時に共通ダイアログのクラス名を整理し、種別切り替え確認を維持する。

この作業では計画書だけを作成する。実装、依存パッケージの追加、PRの公開・マージは実装時に行う。

## Markdown本文と画像の管理

### ファイル構成

| ファイル・ディレクトリ       | 役割                                                    |
| ---------------------------- | ------------------------------------------------------- |
| `src/content/help.md`        | ユーザー向け本文。以後の手編集の入口                    |
| `public/help/images/`        | 本文内の画像。まず `editor-example.png` を配置          |
| `src/pages/HelpPage.tsx`     | ページ見出し、目次、本文、育成計画へのリンク            |
| `src/features/help/`         | Markdown変換、見出し情報、ページ内リンク・画像URLの処理 |
| `src/features/help/help.css` | 本文・目次・画像の装飾                                  |

本文はViteの `?raw` importで文字列として読み込む。Markdownの変更はビルド・公開で反映する。公開先にファイルを直接編集する機能、CMS、MDXは追加しない。

レンダラーには `react-markdown` を採用し、表に `remark-gfm` を使う。見出し処理はremarkの構文木に対する小さなプラグインで実装する。本文を正規表現で別途解析せず、本文と目次を同じ構文木から生成する。必要な型・構文木処理の依存も直接宣言し、実装時に既存のReact・TypeScriptとの適合を確認してバージョンを固定する。コンポーネント置換、プラグイン、GFMの利用方法は [react-markdown公式README](https://github.com/remarkjs/react-markdown) を参照。

通常のMarkdown（段落・箇条書き・強調・リンク・画像・引用・コードブロック・表）を表示する。生HTMLは有効にしない。初期の数式はテキストとコードブロックで十分表現できるため、数式レンダラーは導入しない。

### 画像の挿入方法

画像を `public/help/images/` に置き、本文では次のように書く。

```markdown
![育成計画で職業を追加する画面例](./images/editor-example.png)
```

`./images/` で始まる画像URLは、レンダラーで `import.meta.env.BASE_URL` と `help/images/` を組み合わせたURLへ変換する。たとえばベースパス `/ddda-stat-tuner/` なら `/ddda-stat-tuner/help/images/editor-example.png` となる。Markdownのファイル配置とは別に、この画像記法を編集ルールとしてREADMEに明記する。

サンプルには現行育成計画の画面キャプチャを使用する。入力・成長値の関係が分かる箇所を切り出し、説明の近くに配置する。個人情報や不要なブラウザーUIを含めず、代替テキストと短い説明文を付ける。ダミー画像や外部URLだけの例にしない。表示は `max-width: 100%`、高さ自動とし、モバイルでも本文幅に収める。

READMEには本文の場所、見出しの書き方、画像の保存・挿入例、開発サーバーでの確認、ビルド・公開後の反映を記載する。

## 目次と見出しへの移動

### 自動生成

- ページの `h1` はReact側の「使い方」1つとし、Markdown本文は `##` から書く。
- Markdownの見出しノードを走査して `h2`・`h3` のみを文書順で目次に採用する。コードブロック内の `##`、`h4` 以下は目次に含めない。
- `h3` は直前の `h2` の下に表示する。先頭に `h3` がある場合も欠落させず表示する。対象がなければ目次を表示しない。
- 日本語を保持する見出しIDを生成し、重複や記号だけの見出しにも一意のIDを付ける。全見出しで衝突を避ける接頭辞を付け、目次のリンク先と本文に付与するIDを同じ処理で決める。
- 強調・インラインコード・リンクを含む見出しは、表示テキストを取り出して目次名とID生成に使う。Markdownの装飾記号を目次に表示しない。
- 見出し変更に伴うID変更は許容する。古いIDを指定してもページを壊さない。

### HashRouterとの共存

目次リンクは `#/help?section=<見出しIDをURLエンコードした値>` とする。たとえば概念上 `#/help?section=help-スコアについて` の形式で、経路を `/help` のまま維持する。裸の `href="#見出しID"` でルーターの経路を置き換えない。

`HelpPage` はクエリの変化を受けて、本文描画後に対象を `scrollIntoView` し、`tabIndex={-1}` の見出しへフォーカスを移す。キーボードでも目次リンクから本文へ進めるようにする。直接アクセス・再読み込み・ブラウザーの戻る／進むでも指定節への移動を再現する。存在しないIDは移動を行わず、本文と目次を通常表示する。

本文内に手書きの `#見出しID` リンクを置いた場合も、同じクエリ形式へ変換する。外部リンクと育成計画へのリンクは用途に応じて扱い、外部URLをページ内移動に変換しない。見出しの固定ID指定を必須にせず、本文の通常の編集だけで目次を更新できる仕様にする。

目次は `nav` とリストで構成し、「目次」の名前を付ける。デスクトップでは本文の横、狭い画面では本文の前に置く。装飾は現在の配色に合わせ、見出し・表・コード・画像の可読性を優先する。スクロール後に見出しが隠れない余白と、フォーカス表示を用意する。

### スコアの説明方針

根拠となる実装は `src/domain/status.ts` の `scoreStatus`、比較表示は `growth.ts` と `selectors.ts`、倍数調整の評価は `roundingAdjustment.ts`。

全能力を対象にした式は以下のとおり。

```text
score = HP / 10 + ST / 10 + 物理攻撃 + 魔法攻撃 + 物理防御 + 魔法防御
```

職業カードでは現在の帯の初期値または1Lvあたりの成長値にこの式を適用する。「注目するステータス」で選んだ項目だけを合計し、その値で職業を比較する。全項目を外せばスコアは0になる。一方、倍数調整の前後スコアと評価用スコアは全6能力で計算し、注目項目の選択には連動しない。

本文に掲載する解釈の案：

> HPとSTは他の4能力より数値の尺度が大きいため、10分の1に換算して合計する比較用の指標です。この指標ではHPまたはSTの10点と、攻撃・防御の1点を同じ重みとして扱います。係数は比較のための経験的な設定で、ゲーム内のダメージ式や、すべてのプレイスタイルの強さを表すものではありません。元の実装でこの係数を選んだ厳密な理由は確認できていません。

「尺度をそろえるため」は現在の式に対する合理的な解釈として扱う。過去の採用理由を証明した記述や、10:1がゲームの公式換算であるという説明はしない。計算例としてHPが30増えると全項目スコアは3増え、物理攻撃が3増えても3増えることを示す。

### 倍数調整の説明方針

[Phase 5の探索と保証](phase5-rounding-adjustment.md)、[Phase 6のポーン到達性](phase6-pawn-rounding-verification.md)、現行 `roundingAdjustment.ts` に合わせ、次の順に説明する。既存資料の完全な証明や計測一覧を転載せず、原理・成立条件・保証範囲を簡潔にまとめる。

1. **整数の合同条件として扱う。** 完成した能力値を `S`、職業変更による差を `Δ`、目標倍数を `m = 5 または 10` とすると、全能力について `S + ΣΔ ≡ 0 (mod m)` を満たす職業変更を探す。表示値だけの丸めではなく、育成経路を変更して実際の能力値を倍数にする。
2. **前半と後半に分ける。** Lv1〜10を固定し、Lv11〜100で後半の成長値が満たせる条件を整え、Lv101〜200で残りの剰余を0にする。後半成長はHP/STが5の倍数、HP+STが1Lvあたり20、残り4能力の合計が4という性質を使う。
3. **剰余状態を圧縮する。** `C = 物理攻撃 + 魔法攻撃 + 物理防御 + 魔法防御` とする。前半は `((HP−ST) mod m, ST mod 5, C mod m)` を扱う。10倍数ではHPとSTの剰余がともに0またはともに5、かつ `C mod 10 = 0` となるよう整える。後半はHPの剰余と攻撃・魔攻・防御の剰余を扱い、ST・魔防は合計の制約から決まる。実装の状態数は5倍数で前後各125、10倍数で前半500・後半2,000。ポーンの到達部分集合と実装の配列サイズは区別する。
4. **動的計画法で経路を復元する。** 各区間の元のLv枠を1つずつ処理し、変更しない選択と職業を変更する選択から、剰余状態ごとの良い候補と復元情報を残す。全経路を列挙する必要はなく、候補数による打ち切りも行わない。
5. **強みの低下と変更数を抑える。** 各能力の個別の到達可能最大値を使った損失と全項目スコアの損失を加算する。1変更の評価式を次のように紹介し、変更ペナルティ0.0002、上限超過時0.002、最後に変更数優先で再探索することを説明する。前半ではメイジを新たに増やさない。各能力の最大値はそれぞれの最大値であり、全部を同時に達成できるという意味ではない。

```text
能力損失 = Σ max(0, −Δi) × before_i / max_i²
スコア損失 = 0.25 × max(0, −score(Δ)) / score(before)
評価 = 各変更の能力損失とスコア損失の合計 + 変更ペナルティ × 変更Lv数
```

全200Lvの入力が実行条件であることと、以下の成立条件・上限を本文の表に記載する。

| 種別・目標      | 追加の成立条件                | Lv11〜100 | Lv101〜200 | 合計変更上限 |
| --------------- | ----------------------------- | --------- | ---------- | ------------ |
| 覚者・5／10倍数 | なし                          | 14Lv      | 12Lv       | 26Lv         |
| ポーン・5倍数   | なし                          | 6Lv       | 6Lv        | 12Lv         |
| ポーン・10倍数  | Lv2〜10のメイジ成長回数が奇数 | 9Lv       | 14Lv       | 23Lv         |

ポーンの10倍数条件は偶奇で説明できる。初期 `C` は偶数、Lv2〜10はメイジのみ1Lvあたりの `C` が偶数、他2職は奇数。メイジ回数を `k` とすると、この9Lv分の偶奇は `(1+k) mod 2`。Lv11〜100の90Lv分とLv101〜200の100Lv分は合計が偶数なので、最終 `C` の偶奇も同じになる。4能力が10の倍数なら `C` は偶数であり、`k` が奇数である必要がある。現行成長表の到達性検証により、この条件は十分でもある。Lv1のメイジは `k` に含めない。

保証は現行成長表・種別の職業制限のもとで、成立条件を満たす入力から上限内の解を返すこと。すでに指定倍数なら変更せず、前半条件を満たす場合は前半も維持する。最高スコア、全体の最小変更数、能力の完全維持は保証しない。各変更の損失を加算するため、最終値の増減の相殺を含めた全体最適化ではないことを短く添える。

## PR分割と依存関係

計画をPR 00、実装を2つのPRに分ける。順序は **PR 00 → PR 01 → PR 02**。各PRは直前のPRがマージされた `main` から作成し、それぞれ型チェック・テスト・ビルドが通る状態にする。番号はPhase 7内の呼称であり、GitHubのPR番号ではない。

### PR 00：計画書

範囲：この文書のみ。

受け入れ条件：要望、補完した仕様、技術上の注意点、初期本文の内容、PRの順序と検証範囲が確認できる。アプリの変更を含めない。

検証：文書の整形と差分チェック、現行実装との説明の照合。

### PR 01：Markdown使い方ページ・目次・画像

範囲：Markdown依存の追加、本文とサンプル画像、レンダラー、見出し処理、`HelpPage` とCSS、`/help` 経路、本文・画像の手編集方法をREADMEへ追記。初期本文はこのPRで完成させる。

この段階では `/help` の直接アクセスでレビューできるようにし、既存チャートと使い方モーダルは次のPRまで維持する。新ページの表示・編集方法・内容を先に独立して確認できる状態にする。

受け入れ条件：

- 指定の初期見出し構成と操作・スコア・倍数調整の説明が表示され、現行実装と一致する。
- 見出しの追加・削除・並べ替えで目次が自動更新される。日本語・重複・装飾付き・記号だけの見出しでも目次と本文のIDが一致する。

- サンプル画像が実際に読み込め、代替テキストがあり、390px幅と文字拡大で本文を読める。
- 本文内リンクがルーターの経路を壊さず、画像がルート配信とサブパス配信の両方で読み込める。
