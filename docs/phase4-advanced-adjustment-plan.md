# Phase 4 高度な自動調整計画

## この文書の位置づけ

`workspace/phase4.md` と `workspace/status_adjustment_app_notes.md` を起点に、全ステータスを 5 または 10 の倍数へ調整する機能の仕様、探索方法、実装順、受け入れ条件を定める。この文書の追加時点では計画のみを対象とし、画面や計算処理は変更しない。

## 目的と完了条件

育成計画の「自動調整」に次の 2 種類を追加する。

- 全ステータスを 5 の倍数に調整
- 全ステータスを 10 の倍数に調整

Lv1～200 の全枠に職業が選択されている場合に限り、現在の経路から最大 10Lv 分の職業を、同じレベル帯で選択可能な別の職業へ置き換える。結果の HP、ST、物理攻撃、魔法攻撃、物理防御、魔法防御のすべてが指定した数の倍数であることを必須条件とする。

条件を満たす候補が複数見つかった場合は、既存の `scoreStatus` と同じ計算による **6 ステータスの合計スコアが高い候補を優先**する。スコアは HP と ST をそれぞれ 10 分の 1、残る 4 項目をそのまま足す。育成計画の「注目するステータス」の選択は職業一覧の並べ替え用であり、この調整のスコアには反映しない。同点なら変更 Lv 数が少ない候補、さらに同点なら定義順で安定した候補を選ぶ。変更が 0Lv の現行経路も候補に含めるため、すでに条件を満たしていても、探索範囲内でスコアが高い経路が見つかれば更新する。

「最大 10Lv」は**元の経路で選択済みの枠を最終的に別職業へ変える数**を指す。同じ枠を探索中に何度も変更して 10 回と数える方式にはしない。元の経路に含まれる未変更の枠はそのまま残し、レベル帯ごとの枠数と職業制限を守る。

## 現状と前提

- 現在の自動調整は `src/domain/pathAdjustment.ts` の `maximize-stat` 戦略と `unfilled` 対象範囲で構成され、未選択枠を埋める。新機能は選択済み枠を置き換える別の戦略・対象範囲として追加し、既存の 6 種類の動作を維持する。
- `VocationPath` は Lv1、Lv2～10、Lv11～100、Lv101～200 の帯ごとに職業を配列で持つ。最終ステータスは帯ごとの成長値の合計と体格による ST 加算で決まる。同じ帯では職業の順番を入れ替えても最終値は変わらない。
- 体格の ST 加算は 0、20、40、60、80 なので、5・10 の倍数判定と候補間のスコア順位には影響しない。ただし結果表示のステータスとスコアは現在の体格を含む実値で計算する。
- 空き枠が 1 つでもある場合は新しい 2 種類を実行できない。既存の「未選択レベルを埋める」6 種類は従来どおり空き枠がある場合に実行できる。

## 探索方法

### 状態と候補の作り方

各レベル帯の元の職業別 Lv 数を数える。探索の 1 手は「帯、元の職業、変更先の職業」の組で表し、元の職業から未変更の 1Lv を取り、同じ帯で選択可能な別職業へ割り当てる。1 手の 6 ステータス差分は `変更先の成長値 - 元の職業の成長値` である。元の各職業の Lv 数を超えて取り出さない。手を定義順の非減少順に追加し、同じ入れ替え集合の順序違いを探索しない。

状態には、元の職業から何 Lv をどの職業へ割り当てたか、変更 Lv 数、6 ステータスの余り、現在のスコアを保持する。余りは選択した 5 または 10 に対する値を使う。候補の判定時には既存の `calculateStatus` で組み立てた経路を再計算し、6 項目すべてが実際に倍数になったことを確認する。

採用した職業別 Lv 数を配列へ戻すときは、元の帯で該当する職業が現れる先頭側の枠から、定義順に変更先を割り当てる。これにより同じ探索結果から常に同じ経路を復元し、変更対象外の枠の順序を維持する。元の経路と新しい経路、変更 Lv 数、前後のステータスとスコアを結果として返す。入力の経路は変更しない。

### 探索の上限と候補の選択

10Lv までの全組み合わせはブラウザー向けには大きいため、最初は候補数を制限したビーム探索を採用する。変更 0～10Lv の各深さで次の候補を生成し、余りが 0 の候補を記録する。次の深さへ残す候補は、6 項目の余りから倍数までの循環距離、スコア、変更の割り当ての多様性を使って選ぶ。余りが異なる状態を適度に残し、スコアだけで途中状態を絞らない。最終的に**探索中に発見した有効候補全体**を上記のスコア順で比較する。到達した深さが 10Lv 未満でも、元の経路を含めて比較する。

ビーム幅と展開数の上限は実装時の計測で決め、5・10 のそれぞれで採用値を記録する。上限に達しても有効候補があればその中の最良候補を返す。候補がなければ「設定した探索範囲では条件を満たす経路が見つかりませんでした」と伝え、経路を変更しない。**探索上限内で未発見であることを、解が存在しないという断定に使わない。** ビーム探索は大域的な最高スコアも保証しないため、画面では「探索で見つかった候補の中で最高スコア」と表現する。

探索は大量の状態を扱うため、UI スレッドを長時間占有しない形にする。まず純粋関数として探索を実装し、実測で必要なら Web Worker に分離する。中断できる実行単位を設け、実行中は二重実行を防ぐ。実行中に経路や体格が変わった場合は古い結果を適用せず、実行開始時の入力と現在の入力が一致する場合だけ結果を反映する。性能と応答性の確認結果に基づいてビーム幅・展開数を調整し、10Lv 上限は維持を目標にする。上限を下げる必要がある場合は仕様変更として扱う。

## UI と状態更新

既存の「調整の種類」`select` に 2 種類を追加する。選択した種類に応じて説明、実行可能条件、実行結果を切り替える。

- 倍数調整の説明には、全 200Lv の選択が必要なこと、最大 10Lv を入れ替えること、6 ステータスすべてを対象にすること、候補はスコア優先で選ぶことを示す。
- 倍数調整を選択中で空き枠があれば、残りの Lv 数を示して実行ボタンを無効にする。既存の 6 種類では従来どおり空き枠が 0 のときに無効にする。
- 実行後は変更 Lv 数、調整前後の 6 ステータスとスコア、成功または未発見を確認できるようにする。変更 0Lv の場合はすでに条件を満たしていたことを伝える。
- 探索結果は 1 回の Redux 更新で反映する。チャート、レベル帯内訳、共有 URL と復元は更新後の経路を使う。共有コードの形式は変更しない。

## PR 分割

探索の妥当性と性能を画面変更とは独立してレビューできるため、実装を 2 PR に分ける。各 PR は前の PR を取り込んだ状態から作り、それぞれ単独で `npm run check` が通る状態にする。計画書の追加は実装 PR に含めない。

### Phase 4 PR 01: 探索ドメインと性能検証

**範囲:** 完成経路の判定、5・10 の余りを使った探索、変更 Lv 数とスコアに基づく候補比較、経路の復元、探索上限、結果の種別を React・Redux 非依存の処理として追加する。既存の未選択枠向け処理は維持する。代表的な経路を使った再現可能な性能計測方法と、その結果・採用したビーム幅と展開上限を PR に記録する。

**レビューで確認:**

- 5・10 の両方で、成功結果の 6 ステータスが指定した数の倍数である。
- 変更は最大 10Lv、同じレベル帯内の許可された職業への置換だけであり、元の経路は変わらない。
- 既存経路が条件を満たす場合、変更 0Lv を候補に含める。候補の順位はスコア、変更 Lv 数、安定した定義順に従う。
- 未完成経路と探索上限内で候補が見つからない場合を区別して返す。後者を「不可能」と判定しない。
- 代表例に加え、特定の帯・職業へ偏った経路、9 職業が混在する経路、5 と 10 で難度が違う経路を計測する。展開数、実行時間、発見結果を記録し、画面実装に使う上限を決める。

### Phase 4 PR 02: 自動調整 UI と全体検証

**範囲:** 2 種類の選択肢、説明、実行可否、探索中表示、結果と未発見の通知、古い探索結果の適用防止を育成計画に接続する。必要な場合は探索を Web Worker で実行する。README とヘルプを実際の操作に合わせて更新する。

**レビューで確認:**

- 未完成経路では倍数調整を実行できず、既存の未選択枠を埋める自動調整は使える。全枠が埋まると条件が逆になる。
- 5・10 のそれぞれで成功、変更 0Lv、未発見を区別して表示する。実行中も画面操作と結果通知が成立し、二重実行しない。
- 適用結果のステータス、内訳、チャート、共有・復元が一致する。
- 探索中に手動編集・体格変更・復元が起きても、古い結果で現在の状態を上書きしない。
- 幅 390px 相当でも説明と結果を読め、キーボード操作と読み上げで実行可否と結果が分かる。
- `npm run check` と `npm run test:e2e` が通る。

## 検証上の注意

小さな変更数については全列挙による比較をテスト用に行い、探索結果が有効であることと、発見済み候補の選び方を確認する。10Lv 全域での大域最適性は受け入れ条件にしない。性能検証はブラウザー実行も含め、メインスレッドの停止、探索上限到達時の通知、経路変更中の古い結果の扱いを確認する。実装時に新しい依存関係や探索方式へ変更する場合は、計測結果と変更理由を PR に残す。
